ER図：Firestore のデータモデル

すべてのデータは `users/{uid}` の下にある。クライアントから Firestore へ直接は読み書きせず（`firestore.rules` は全拒否）、API Routes が Admin SDK で読み書きする。

`PK` は文書 ID、`FK` は別の文書 ID を指す項目。Firestore は外部キー制約を持たないので、関係はアプリが守る。

補足：

  • `THOUGHTS` には、移行完了まで旧6項目（event・thinking・action・reason・emotion・values）と旧 embedding が残る。図からは省いた。
  • 記録を消すと、そのチャンクも消え、手紙・相談の `refs` は `deleted: true` で引用を伏せる（憲法第13条）。
  • 下書きはサーバーに送らず、端末の localStorage だけにある。

シーケンス図：記録の保存（日記 → 深掘り → 保存 → 裏でメタ）

本人の文章は書き換えず、そのまま `thoughts` に保存する。検索用の1行メタは、保存の応答を返したあとに裏で作る。

sequenceDiagram
    actor U as 本人
    participant C as 画面(記録タブ)
    participant P as proxy.ts
    participant API as API Routes
    participant DB as Firestore
    participant O as OpenAI(embedding)
    participant H as Claude Haiku 4.5

    U->>C: 日記を書く(端末に下書き保存)
    C->>P: POST /api/deepdive(トークン付き)
    P->>P: IP回数制限 / App Check検証
    P->>API: 通す
    API->>DB: 深掘りの利用枠を1つ消費
    API->>H: 日記 + 共通部 + 深掘りの追記
    H-->>API: 質問1つ
    API-->>C: 質問
    U->>C: 答える(スキップ可) → 長押しで保存
    C->>API: POST /api/thoughts
    API->>DB: 記録の利用枠を1つ消費
    API->>O: 本文をチャンクに分けて embedding
    O-->>API: ベクトル
    API->>DB: トランザクションで thought と chunks を保存
    API-->>C: 完了(危機の言葉があれば crisis:true)
    C->>U: ホームへ(crisisなら窓口を案内)
    Note over API,H: 応答のあと after() で続行
    API->>H: 本人の言葉 + 日付(メタ生成の追記)
    H-->>API: 出来事・感情・場面の1行
    API->>O: 本文 + メタで embedding を作り直す
    API->>DB: 本文が変わっていなければ chunks のメタと embedding を更新

出典：`app/api/deepdive/route.ts`・`app/api/thoughts/route.ts`・`lib/db/chunkStore.ts`・`app/(tabs)/record/useRecordSession.ts`。

補足：

  • 一言（`quick`）はAIを呼ばず、気分から作った固定の1行をメタに入れる。裏のメタ生成は `full` だけ。
  • 深掘りの上限に達した日（429）は、質問なしで日記を保存できる。
  • 過去日に書いた記録は、その日にすでに記録があると 409（`date_taken`）で断る。

シーケンス図：相談（過去の自分の記録を根拠に答える）

AI に渡すのは、本人の言葉のチャンク（日付つき）と相談の文だけ。気分・メタ・題・呼び名は渡さない。

sequenceDiagram
    actor U as 本人
    participant C as 画面(相談タブ)
    participant API as POST /api/consult
    participant DB as Firestore
    participant O as OpenAI(embedding)
    participant M as Claude Opus 4.8

    U->>C: 質問を送る
    C->>API: message と chatId(あれば)
    API->>DB: 相談の利用枠を1つ消費
    alt 上限に達した
        API-->>C: 429 daily_limit
    end
    API->>DB: スレッドの履歴を読む(直近20件)
    API->>O: 直前の発言 + 今回の質問で embedding
    API->>DB: chunks をベクトル検索(上位5記録・しきい値0.3)
    alt 検索結果が3件未満
        API->>DB: 利用枠を戻す
        API-->>C: 409 not_enough_records
    end
    API->>DB: スレッドがなければ作る
    API-->>C: chatId と参考にした記録(refs)
    API->>M: 共通部 + 相談の追記 + 履歴 + 本人の言葉と日付 + 質問
    M-->>API: 回答(ストリーム)
    API-->>C: 回答を少しずつ送る
    API->>DB: 質問と回答を messages に保存(refs つき)
    C->>U: 回答 + 参考にした記録

出典：`app/api/consult/route.ts`・`docs/DEVELOPMENT.md`（フォールバック）。

補足：

  • チャンクがない人は、旧 `thoughts.embedding` の検索にフォールバックする。
  • 失敗したときは利用枠を戻し、作ったばかりの空のスレッドは消す。
  • 会話（`messages`）は RAG に入れない。

シーケンス図：週の手紙（開いたときに生成）

スケジューラは使わない。手紙を開いたときに生成を始め、画面を閉じても裏で最後まで続く。

sequenceDiagram
    actor U as 本人
    participant C as 画面(手紙)
    participant API as /api/letters/current
    participant DB as Firestore
    participant M as Claude Opus 4.8

    U->>C: ホームの手紙カードをタップ
    C->>API: GET
    API->>DB: 今週の手紙を読む
    API-->>C: ready / generating / none / locked
    alt none(まだ書かれていない)
        C->>API: POST
        API->>API: 開ける週か(日曜から翌土曜) / 記録が3日以上か
        API->>DB: 手紙の利用枠を1つ消費
        API->>DB: トランザクションで generating にする(二重生成を防ぐ)
        API-->>C: 202 generating
        Note over API,M: 応答のあと after() で最後まで続ける
        API->>M: 共通部 + 手紙の追記 + 今週の記録(日付つき・本人の言葉)
        M-->>API: 手紙の本文
        API->>API: 引用が本人の文章の部分文字列かを検証
        alt 成功
            API->>DB: ready で保存(今週の玉も一緒に)
        else 失敗かつ危機の言葉のある週
            API->>DB: 固定文の手紙(窓口の案内)を保存
        else 失敗
            API->>DB: 作りかけの手紙を消して利用枠を戻す
        end
        loop 4秒ごとに GET
            C->>API: GET
            API-->>C: generating
        end
        C->>API: GET
        API-->>C: ready と手紙
    end
    C->>U: 封が開く → 便箋

出典：`app/api/letters/current/route.ts`・`lib/db/letterStore.ts`・`lib/db/useLetter.ts`（再取得の間隔 4000ms）。

補足：

  • 開けない週は 409 `not_available`、記録が3日未満は 409 `too_few_records`（AI は呼ばない）。
  • 失敗かつ危機の言葉のない週は、固定文の手紙は作らず、手紙を消して枠を戻す。次に開いたときにもう一度作る。
  • 生成中のまま6分以上止まった手紙は、次の POST で作り直す（前の生成が使った枠を戻す）。
  • 別のタブが先に作っていた場合は、利用枠を戻して、その手紙を返す。

状態遷移図：手紙（`letters/{weekKey}` と画面の状態）

画面が受け取る状態は `locked / none / generating / ready`。手紙のドキュメントに保存されるのは `generating` と `ready` のとき。

stateDiagram-v2
    [*] --> locked: 今週の記録が3日未満
    [*] --> none: 記録が3日以上・手紙がまだ無い
    locked --> none: 記録が3日に達した
    none --> generating: 開いて POST(利用枠を消費)
    generating --> ready: 生成・検証に成功して保存
    generating --> ready: 失敗したが危機の言葉のある週(固定文の手紙を保存)
    generating --> none: 失敗(作りかけを消して利用枠を戻す)
    generating --> generating: 6分以上止まっていたとき POST で作り直す
    ready --> ready: 初めて開く(readAt を記録)

出典：`app/api/letters/current/route.ts`（GET・POST・`generateLetter`）、`lib/db/letterStore.ts`（`decideBegin`・`GENERATING_STALE_MS` = 6分）。

補足：`LetterStatus` の型には `failed` があるが、コードのどこにも `failed` を書き込む処理は無い（保存値が未知のときの読み取りの既定値としてだけ使われる）。そのため図には入れていない。
